# STRATA: Descent

A first-person dungeon crawler in three.js. Every image in the game — walls, floors,
enemies, items, icons — is generated by **Z-Image Turbo** through the ComfyUI MCP
server; the maze, the difficulty curve, the loot and the combat are procedural.

Design document: [`GAME_DESIGN_SPEC.md`](GAME_DESIGN_SPEC.md) — the build follows it,
and the spec has been updated wherever implementation proved it wrong.

## Running it

```
npm install
npm run dev          # http://localhost:5177
```

Click **Descend** to play. The art is ~57 MB of 1024² PNGs, so the first load takes a
few seconds; a progress bar shows on the menu.

Source edits hot-reload. New or replaced **images** need a dev-server restart, because
the image list is resolved when the server starts (see *Dev notes*).

## Controls

| Input | Action |
|---|---|
| Mouse | Look (pointer lock) |
| `W A S D` | Move |
| `Shift` | Run |
| Left click / `Space` | Attack |
| `1` | Melee weapon |
| `2` | Bow (refused if you have no bow, or no arrows) |
| `E` / `F` | Interact (stairs, chests) |
| Hold on stairs | `1.5 s` to descend |
| `Esc` | Pause |
| Paused: `L` then digits | Playtest cheat — jump the run to that depth (`L 0 5` → depth 5, `L 1 0` → depth 10) |
| `M` | Mute |
| `V` | Fullscreen (F11 also works, but leaves the canvas at its CSS size) |

### Fullscreen

A run **goes fullscreen by itself** when you press NEW RUN, because a page may only enter
fullscreen on a gesture you made — the click is that gesture. Decline it in Settings ("Go
fullscreen when a run starts") or with `?fullscreen=0`. `Esc` leaves fullscreen, and `V` toggles
it at any time. iPhone and iPad Safari cannot do this for a page, so there the game fills the
window as usual.

Walk over an item to pick it up. Better gear equips itself into its own slot — a bow never
replaces the sword in your hand — and worse gear is sold for gold. Bows are fired with
arrows: every shot spends one, archers drop 1–3 when they die, and when the quiver runs
empty the sword goes back in your hand and `2` does nothing until you find more arrows.
Health comes back only from potions.

## Tests

```
npm test              # levels + loot + movement + file-name case + sprite-animation keying (Node, ~35 s)
npm run test:case     # every asset key the code names matches the spelling on disk
npm run test:video    # the animation keyer: compose a sprite on a measured backdrop, key it back out
npm run test:game     # boots the real game in headless Edge, 42 integration checks
npm run test:keys     # chroma-key QA: measures every generated sprite, non-zero exit if one keys badly
npm run build && npm run check:build   # the built site, served as plain static files, not the dev server
```

All currently pass: 200/200 generated levels solvable, the loot spread
checks, the collision checks, the file-name case audit (every asset key the code names
matches the spelling on disk, which any case-sensitive host such as Pages requires),
42/42 integration checks (including that opaque chroma art and genuinely transparent RGBA art
are told apart and keyed accordingly, and that WASD and the arrow
keys move the way the camera actually points, that every prop kind resolves to geometry or
real art, that no torch floats free of a wall, that each enemy family ramps its silhouette
by tier, that the splat and trail effects are wired to the creatures they were drawn for,
that an archer's shot travels toward the player, that a pedestal bow sits beside a quiver of
five arrows, that the pause cheat `L` + digits jumps the run to a real generated depth, and
that the quiver gates the bow: a shot spends an arrow, an empty quiver hands the blade back
and refuses `2`, and an archer's carcass yields between 1 and 3 arrows), and 57/57 sprites
key clean.

Art QA, which renders a report you can look at instead of reading numbers:

```
npm run qa:seams      # seamcheck.png — every tile at 50% offset vs. the engine's mirrored pass
npm run qa:keys       # keycheck.png  — every sprite after the real keying pipeline, with numbers
npm run qa:props      # propcheck.png — every solid prop, front view and turned 40 degrees
npm run qa:props:one -- "?only=staircase"   # one prop, framed from standing eye height
npm run qa:props:one -- "?only=torch"         # in that mode the lighting is copied from the game
npm run qa:fx         # fxcheck.png — every effect composited the way the engine draws it
npm run qa:alpha      # alphacheck.png — keyed sprites vs RGBA ones, with alpha measurements
npm run qa:anim       # animreview.png — every clip rendered so far: frames, numbers, verdicts
npm run qa:arrow      # an archer's arrow frozen in flight, coming at the camera

npm run shot -- index.html play.png 1280 720 "?demo=1&seed=alpha&depth=9&preview=orc&tier=4"
```

Each starts its own Vite server, so they work whether or not `npm run dev` is running.
The game page preloads 88 textures, so `SHOT_BUDGET=150000 npm run shot -- index.html ...`
raises the headless time budget when a screenshot comes back empty. A shot can also fail
while the art pipeline is mid-write — PNGs being replaced under the dev server can break the
page's preload — so re-run it after a generation batch lands. `test:game` is immune, because
the self-test skips art preloading.

`test:game` needs a Chromium browser installed; it uses a throwaway profile, so it will
not disturb an open browser window. Individual suites: `test:levels`, `test:loot`,
`test:movement`.

## Sharing it: GitHub Pages

The built game is plain static files — HTML, ES modules, CSS and the generated PNGs. No
server, no database, nothing that runs after the page loads, and nothing the visitor needs
Node for. So it can live on Pages.

Three steps, once:

> **Plan check first.** Pages can only be served from a **public** repository on a free
> GitHub account, and a **private** repository's Pages site is access-controlled: only people
> GitHub lets into the repository can load the site. With Pro, publishing from this private
> repository works, and the URL for this one is `https://duffyjp.github.io/dungeon-game/` —
> friends need to be collaborators until the repository is made public, which needs no other
> change. Either way the workflow also leaves a `strata-site` zip under the run's Artifacts
> tab, which Cloudflare Pages or Netlify can serve from a private repository at no cost.

1. Push the repository to GitHub (`git remote add origin …`, `git push -u origin main`).
2. In the repository's **Settings → Pages**, set **Source** to **GitHub Actions**.
3. Push. `.github/workflows/deploy.yml` runs the test suites, builds `dist/` and publishes
   it. The URL appears on the workflow run's summary page; every push to `main` redeploys,
   and the Actions tab can run it by hand.

Check the build the way a visitor receives it before publishing:

```
npm run build
npm run check:build
```

`check:build` deliberately does not use the dev server. It serves `dist/` from an ordinary
static file server, runs the full integration suite against that, and loads every generated
image the way a first visit does. It fails if `index.html` references an absolute path — a
project site is served under `/<user>/<repo>/`, which is why the Vite config uses
`base: './'` — or if the build is missing `music/manifest.json` (copied out of
`assets/music/` by a small build plugin, because a hosted page cannot read your source
tree) or `.nojekyll` (kept in `public/`, telling Pages not to run the site through Jekyll).

Two limits, both from Pages rather than from the game: the whole site is about **53 MB**,
which is a real first download, and Pages allows 1 GB of storage and roughly 100 GB of
bandwidth a month — comfortable for sharing with friends, not for a launch on a front page.
The tiling textures are most of the weight and are the one part that could be lossily
compressed without disturbing the chroma-key pipeline the sprites depend on.

The workflow runs `npm test` before it publishes, and that now includes a file-name case
audit: Windows treats `Wall_Crypt.png` and `wall_crypt.png` as the same file, the Linux
runner and Pages do not, and a mis-cased reference arrives as a 404 that the game papers
over with a grey placeholder. `tools/caseCheck.mjs` compares every asset key the source and
data name against the exact spelling on disk and fails the build on a mismatch.

**A test may not require a machine-local tool.** `npm run test:video` decodes shipped sprites,
which means ffmpeg for the WebP ones — and a GitHub runner has no ffmpeg (and no `git`-ignored
`sprite_sources/` masters either). It probes `FFMPEG`, then `PATH`, then the Windows location, and
reports anything it cannot read as a skip: `16 passed / 0 failed / 7 skipped: ffmpeg not
installed`. `FFMPEG=off` forces that path so it can be tested on a machine that does have it. A
hard-coded `C:\ffmpeg\bin\ffmpeg.exe` in that suite took the Pages deploy down for an hour, which
is how this rule got written.

## ComfyUI boxes, and which model may be used at all

Three probes, because model advice is worthless without the hardware and the licence:

```
node tools/comfyStats.mjs                 # the box the MCP server talks to: GPU, VRAM, installed models
node tools/findComfy.mjs                  # what ComfyUI servers exist on the LAN
node tools/probeHost.mjs 10.1.1.1         # which port a given machine actually serves (accepts ranges)
```

- **`http://10.0.0.99:8000`** — the box the art pipeline is bound to. RTX 2060, 12 GB, about
  1 GB free while the Z-Image pipeline is resident. No upscaler, ControlNet or IP-Adapter
  models installed. Everything in `assets/images/` came from **Z-Image Turbo, which is Apache
  2.0**, so every shipped pixel has a clean chain of title.
- **`http://10.1.1.1:8188`** — the second machine: **RTX 5070 Ti, 16 GB with ~14.7 GB free**,
  ComfyUI 0.44, reachable since ComfyUI there was started with `--listen 0.0.0.0`. It holds
  **Qwen-Image-2.1** (int8) plus an image-*editing* graph, and also `z_image_turbo` in bf16 and
  int8, so the Apache-licensed house model can run on the faster card too. Upscalers and
  ControlNets are still not installed on either box.
- **Licensing, and the decision recorded against it.** Qwen-Image-2.1 ships under the **Qwen
  Research License**: "Non-Commercial shall mean for research or evaluation purposes only",
  with commercial use requiring a separate agreement, and a quantised conversion inherits
  that. The repository owner reviewed the terms on 2026-11-06 and is comfortable shipping
  images from it. That decision is only safe if it is auditable: every asset made with a
  non-Apache model must record the model and licence in `assets/images/manifest.json` (and
  `workflows/*.json` carries the note next to the graph), so "which pixels came from where"
  is a lookup rather than a memory.

## Trying the second box: real transparency instead of a magenta field

The chroma-key pipeline is a workaround for a generator that cannot emit alpha. The Qwen box
can, but only if you ask in a specific way and then check what came back.

```
# 1. Ask with the alpha framing, enhancer switched off so the wording reaches the image model
node tools/comfyRun.mjs --graph workflows/qwen_image_edit.json \
  --upload assets/images/vfx/ghost_trail.png --image-node 470 \
  --set "459:484.switch=false" \
  --set "459:484.on_false=the image contains an alpha channel. Remove the background so the subject floats on nothing, keeping the subject itself unchanged: same shape, same colours, same soft feathered edges transparent background" \
  --set "459:458.seed=44210" --set "461.filename_prefix=strata-alphaframed" --out experiments/qwen

# 2. Validate it. Never trust "it saved a PNG".
node tools/pngAlpha.mjs experiments/qwen/strata-alphaframed-44210_00001.png

# 3. Repair the edge band, then look at it in context
node tools/alphaDespill.mjs experiments/qwen/strata-alphaframed-44210_00001.png experiments/qwen/vapour.png
npm run qa:alpha
```

- **Without the framing it does not work.** Asked plainly to remove the background, the model
  paints the field **white** and writes alpha 255 across the whole frame: colour type 6,
  measured 0.0% clear pixels. A checker or an eyeball at thumbnail size both read that as
  "transparent". The framing that does work starts the instruction with
  *"the image contains an alpha channel."* and ends it with *"transparent background"*, with
  the graph's prompt enhancer switched off so nothing paraphrases it away: measured 29–30%
  clear, 15–18% opaque subject, across three seeds.
- **The soft edge comes back violet, and it is the model's doing, not the input's.** Feeding a
  magenta field gave an edge band of `rgb(166, 89, 200)`; feeding a white field gave
  `rgb(179, 113, 207)`. Over stone floor that is a purple halo — the pink-fringe complaint
  wearing a different hat. `tools/alphaDespill.mjs` pulls only the semi-transparent band toward
  the subject's own core colour and leaves every opaque pixel untouched: `rgb(216, 80, 220)`
  (magenta 0.53) became `rgb(218, 217, 221)` (magenta 0.00) with the alpha distribution
  unchanged.
- **It is a generator, not a cutout tool.** It repaints the subject while removing the
  background — the vapour came back bigger and billowier — so it can't convert approved art
  losslessly. Judge every attempt: the run prints clear/soft/opaque shares and a verdict, and
  flags a coloured fringe; `tools/testPngAlpha.mjs` keeps the measurer itself honest (8 unit
  tests, part of `npm test`), including the exact false positive of an RGBA file whose alpha is
  opaque everywhere.
- **Engine side:** `render/assets.js` detects a real alpha channel from the pixels and skips
  chroma keying for that asset, so keyed and transparent art can share a folder. Asserted both
  ways by the integration suite (42/42).
- **The full pass, run 2026-11-06:** 49 billboards (23 enemies, 18 items, 8 effects) through
  `tools/alphaBatch.mjs`, all 49 measured, accepted on three numbers — background removed,
  subject present, and silhouette overlap against the approved art. Overlap came back 0.596 to
  0.995, median 0.96: the model holds a silhouette far better than it looked in the first
  single-asset test. `npm run review:alpha` renders only the ones under 0.9, which is the list
  a human has to look at, and `npm run promote:alpha` promotes the rest — with a `--min-iou`
  gate (default 0.9), a resize to 512 px because a billboard never draws bigger and the raw
  files are 1024², and a backup of every replaced file under `assets/images/_chroma_v1/`.
- **Still broken:** the server-side colour-mask cutout (`workflows/alpha_cutout.json`).
  `ColorToMask` returns a uniform mask whatever threshold and polarity I give it, so the output
  is either all clear or all opaque. The box has SAM3 nodes, which is the better tool for
  hard-edged sprites; that path is untried.
- **Nothing from `experiments/` ships.** The folder is gitignored and outside the asset glob;
  promoting an experiment means moving it into `assets/images/` and recording the model and
  licence in the manifest in the same change. Graphs live in `workflows/` with their patch
  rules written beside them — same discipline as `z_image_turbo`, different model.

## Animating sprites: Wan 2.2 image-to-video

Sprite animation runs on the 5070 Ti box, and it runs on **Wan 2.2 because of its licence** —
Apache 2.0, no revenue or field-of-use clauses — rather than the LTX-2 community licence or
MiniMax's proprietary terms, which would put shipped assets under conditions we have not
agreed to. See `GAME_DESIGN_SPEC.md` 13.8 for the full reasoning.

```bash
npm run anim:check                          # validate the graph against the server, before queueing
npm run anim:clip -- --sprite enemies/t1/slime --action walk
npm run anim:phase                          # the whole phase, strictly one clip at a time
npm run anim:measure                        # re-judge every clip on disk under today's gates: no GPU
npm run test:video                          # the keying/motion maths, tested on shipped sprites
npm run qa:anim                             # animreview.png — contact sheets and verdicts
```

What the measurements taught us, in the order they arrived:

- **Check the graph against the server before spending a queue slot.** `tools/graphCheck.mjs`
  reads `object_info` and confirms every node class, every input name — including ComfyUI's
  flattened `values.a` / `format.codec` sub-widgets — and that every model file the graph names
  is actually in that loader's list. It found that this graph is structurally invalid on the
  2060 art box, whose `CreateVideo` predates four of its inputs.
- **Frame counts must be 4n+1**, because Wan's video VAE compresses time by 4. The graph
  derives its length from `floor(duration * fps + 1)`, so the tool sets duration to
  `(frames − 1) / fps` and asks for exactly the count it wants: 17 for a step cycle, 13 for a
  single strike.
- **The backdrop is measured per sprite, never chosen by hand.** `tools/videoKit.mjs` projects
  each sprite's own opaque pixels onto every candidate backdrop's hue axis and takes the 95th
  percentile as a collision score. Green loses to blue on the slimes (0.52 against −0.15) and
  wins for the spiders (−0.01): a hand-picked chroma colour would eat the slime's body and
  survive on the spider, backwards. Keying uses the same rule as the runtime keyer, generalised
  from magenta to an arbitrary hue axis, and `npm run test:video` proves the compose-then-key
  round trip on shipped art before a GPU minute is spent.
- **Wording beat the sampler.** The 4-step lightx2v LoRA path at CFG 1 took 15 s and looked as
  good as the 20-step CFG 3.5 path at 57 s from the same start frame; what changed the result
  was asking for large exaggerated steps instead of a "steady rhythm". A whole phase is
  therefore minutes, not hours — and prompts stay anatomy-free, because naming a body part the
  sprite does not have makes the model grow it.
- **A clip can pass every consistency gate and still be a still photograph.** So movement is
  measured on its own terms — how much of the silhouette's coverage changes per step — and a
  frame compared with itself scores zero. Floor: 0.6%.
- **The first clips did not fail by going still; they failed by turning.** One clip rotated the
  creature sideways while its centroid sat perfectly still, so "camera stayed put" said nothing.
  The silhouette's bounding box gives it away: the turning clip bottoms out at 0.82 of the first
  frame, clips that stepped in place stay above 0.87, hence a 0.85 floor — exempt for `flee`,
  whose job is to shrink. It is a proxy, which is why every clip also gets a contact sheet.
- **Motion is bought with identity.** As movement rose from 0.94% to 1.36% of the frame per
  step, worst silhouette overlap against the still fell from 0.80 to 0.64. Both ends are gated.
- **Gates can be tightened after the fact.** `tools/animMeasure.mjs` re-scores clips already on
  disk and rewrites their verdicts, so a rule learned late re-judges the whole phase instead of
  leaving stale ACCEPTED stamps behind.
- **One generation in flight at a time**, always: `tools/animBatch.mjs` is a serial loop, and
  clips already accepted are skipped, so an interrupted phase resumes where it stopped.
- **Nothing promotes itself.** Clips land in `experiments/anim/<sprite>__<action>/` with the raw
  clip, per-frame keyed PNGs, a contact sheet and measured `results.json`; moving animation into
  the game is a separate, deliberate step.

### Shipping the animation: animated WebP, boomeranged, frames named at runtime

```bash
npm run anim:webp -- --only cellar_spider__walk        # build one, verify the container
npm run anim:webp -- --yes                             # publish into assets/anim/
npm run qa:animprobe                                   # what the browser can and cannot do
```

- **Boomerang lives in the file:** frames go 1…*N* then *N*−1…2, endpoints not duplicated, loop
  forever. A model-rendered clip starts at the still and drifts; it does not come back
  seamlessly, and reversing it costs no pixels.
- **The file does not play itself.** An `<img>` of an animated WebP gives the canvas one frozen
  frame — verified, not assumed — and the game has to name a frame because every creature sits
  at a different moment, the player can pause, and an idle monster should show its still sprite.
  So frames are decoded by index with WebCodecs `ImageDecoder` and shared per clip; if that API
  is missing the whole feature switches off and the game behaves exactly as before.
- **Two API traps, both cost an hour:** `ImageDecoder` wants an ArrayBuffer (a Blob throws a
  type error that reads like the API is missing), and this build reports a null `selectedTrack`
  and `complete: true` on the first frame — so the frame count comes from the container, which
  `tools/webpParse.mjs` reads from the RIFF chunks because ffmpeg cannot re-read its own
  animated WebP and `webpmux` is not installed.
- **Verified before kept:** animation flag, loop-forever count, frame count, canvas size and a
  per-frame alpha plane. A file that fails any of those is deleted, not shipped.
- **Cost, whole roster:** 49 clips = **4.6 MB**, payload 38.0 → 42.2 MB. Walk and attack for
  all 23 distinct enemy drawings, flee only for the three spiders — retreating is spider-only
  AI, so flee animations for the rest could never be seen. Each clip is 10 unique frames
  boomeranged to 18, at 152 px, quality 70. The same roster at 192 px with every frame
  projects near 18 MB, which is why the settings are arguments rather than constants.
- **8-bit indexed WebP was tried and rejected on measurement:** palette encoding came out 3×
  larger lossless and no smaller lossy than plain RGBA at quality 60, because ffmpeg
  re-expands it internally. Frame count and cell size are the levers that actually work.
- The build check's browser budget had to rise (220 s → 420 s): decoding 32 frames is real work
  that virtual time does not fast-forward, and the failure mode was a misleading "page did not
  boot".

## Music

`assets/music/` holds eight ambient cues from the project owner's own backlog, generated with
**ACE-Step 1.5**, re-encoded to 128 kbps MP3 and level-matched: one per biome (`crypt`,
`cavern`, `foundry`, `vault`), a `boss` cue, a `title` theme, and two extra cues for variety.
30.3 MB of music for 33 minutes of playing time; the 78 MB originals live in `music_sources/`,
which git ignores, so the masters survive the re-encode.

The game picks by filename prefix: `cavern_02.mp3` belongs to The Caverns and a depth with a
boss prefers the boss cue. Nothing matches a biome, or there is no manifest, and it falls back
to a shuffle bag over everything in the folder. Cues do not hard-loop — one ends and the next
starts through a 1.2 s crossfade — because a measured start/end level difference of more than
a few dB makes a hard loop click.

```
npm run music:pack -- --map "ACE_Step1.5_xl_turbo_00018_ = crypt" --map "long_track = cavern@auto"
node tools/audioProfileSelftest.mjs
```

`tools/musicPack.mjs` re-encodes, level-matches to a −20 dBFS mean, and can trim silence off
the front of a cue (`@auto` cuts the measured lead-in, `@24` cuts 24 seconds). It writes to
`experiments/` first, so you check the names before anything lands in the game. The slot names
matter because biome selection is by prefix; `tools/audioMeter.mjs` also profiles a track's
darkness, brightness and onset rate, and `tools/audioProfileSelftest.mjs` checks that profiler
against pure tones — which is how a bad version of it got caught before it decided the
soundtrack.

`credits.json` records where each cue came from and ships inside the build; `manifest.json` is
optional and only pins play order or excludes tracks.

## Sound effects

35 events — swings, hits, bow, spells, creature vocalisation, pickups, stairs, UI and the
distant ambience stings — are generated with **Stable Audio 3 medium** on the 5070 Ti box and
live in `assets/audio/sfx/<event>.mp3`. The synthesised WebAudio recipes in spec §12.2 are
still in the file as a fallback: a missing clip plays the placeholder rather than silence,
which is why the self-test asserts that every event has a generated file.

```
node tools/graphCheck.mjs workflows/stable_audio_sfx.json http://10.1.1.1:8188   # validate the graph
npm run sfx:batch -- --all                    # generate the whole bank, one at a time
npm run sfx:batch -- --only hit_metal,bow_draw --seeds-from 46100    # re-roll rejects
```

Edit wording in `workflows/sfx_prompts.json`, not in the graph: the graph's reprompt chain was
removed so descriptions reach the model verbatim, which is what makes a prompt replayable.
`tools/sfxBatch.mjs` measures each clip from decoded samples and rejects defects you would
otherwise notice late — a clip that clips at 0 dBFS, dead air before the attack, a hard cut
instead of a decay, a length that disagrees with the request — then level-matches survivors to
a −6 dBFS peak so a water drip doesn't land as loudly as a boss roar. Levels, seeds and
measurements for every accepted clip are in `experiments/sfx/results.json`.

Licence: the model is tagged `stable-audio-community` on Hugging Face and the upstream repos
are gated behind Stability's terms. Ask before shipping more of its output; the answer belongs
in the manifest, not in a guess.

## Art pipeline

`assets/images/manifest.json` records every image: slug, prompt, seed, size, steps,
filename prefix and the ComfyUI source URL. Prompts are listed in spec §13.5, seeds
are recorded per asset, and a retry records the rejected seed.

Batch 1 (16 textures + 23 enemies, seeds 41000–41038) and batch 2 (8 props + 18 items
+ 8 VFX + 15 UI, seeds 42000–42048) were generated strictly one at a time — the Z-Image
server on the other PC handles a single generation at a time. `items/arrow` took three
attempts; the two rejected seeds are recorded in its manifest entry.

## Performance: measure, then guess

`?profile=1` puts a frame-time readout on screen and prints one line every two seconds:

```
[perf] frame p50 16.7ms p95 23.1 p99 41.0 max 88.0 (raf min 16.6) | cpu update 2.4ms + submit 5.1ms
       | 158 draws, 175k tris, 38 programs | pixel ratio 2, 6 pooled lights
```

`p50` is smoothness, `p95`/`p99`/`max` are the stutters — a game can feel bad with a good median.
`cpu` is what the game itself costs; the gap between that and the frame interval is the GPU. Note
`render()` returns before the GPU finishes, so submit time is not GPU time. **`raf min` is the
shortest interval the browser handed us: if the median sits on it, the frame clock — not the
drawing — is the ceiling.**

A/B the suspects without editing code:

| URL | What it tests |
|---|---|
| `?noscene=1` | draws nothing at all: if the interval is unchanged, the cap is the display or the browser, not the game |
| `?ratio=0.75` | renders below native pixel count (only a change if `devicePixelRatio` is above that) |
| `?lights=4` | the torch light pool — every light is a full BRDF evaluation in every fragment |
| `?disp=0` | height-displaced walls (223 wall instances, most of the triangles) |
| `?aa=0` | multisample antialiasing, mostly wasted above 1x |

Before the first frame is playable, the game now uploads every texture and compiles every shader
variant the level will use (`[gpu] depth 1: 596 textures, 38 programs in 0.4s`). three.js uploads
a texture on first draw and compiles a material on first use, which put a **one-second stall on
level entry** and left shader programs climbing from 12 to 21 in the middle of a fight — cost the
network panel cannot show, because the bytes were already downloaded.

Known costs at a mid depth: **158 draw calls, 175k triangles, 12 point lights + 1 spotlight
compiled into every material, pixel ratio up to 2.** Dropping loot does not recompile anything,
and the minimap repaints at 20 Hz rather than every frame.

What the four runs above actually showed on the owner's machine: `p50` stayed at 31–32 ms with
**nothing drawn** and with a 7× smaller framebuffer, so that number is the display's frame clock
(≈30 Hz — check Windows → Display → Advanced display → refresh rate, and the cable), not the
game. The hitches were `p99`/`max`: shader programs climbing `12 → 40` mid-fight because every
effect disposed its material on fade-out, which frees the compiled program, and this GPU has no
parallel shader compile. Effects now share one quad, never dispose their materials, and get
prewarmed before play begins.

## Loading: what a depth needs, before it plays

Assets used to arrive just-in-time, which meant the first wraith of a new tier, the first wall
of a new biome and the first step of any animated monster each downloaded and decoded mid-fight.
A depth now works out what it will draw — biome surfaces and their derived maps, the prop kinds
that level actually generated, the enemy families the spawner is allowed to place at that tier,
and their animation clips — and loads all of it behind a progress card before the level exists.

```
src/world/levelAssets.js      what a depth needs (the same rules the renderer and spawner use)
src/render/assets.js          warmAssets / warmAsset, plus the cold-request counter
src/main.js                   preloadLevelAssets, the DESCENT progress card
```

- Boot loads nothing heavy; the menu appears immediately. The art that any moment can need
  (item icons, effects, HUD frames) rides along with the first descent, and the **sound bank is
  decoded in the background while the menu is up** — 35 files, about 1.4 MB. Fetching an effect
  on first use cost a round trip inside a sword swing: 56 ms for a single 26 KB effect that was
  already in the browser cache, because even a cached file pays a `304` revalidation.
- A cold band costs about 74 images and 13 clips — roughly 2 MB — paid once per biome/tier
  change, not per depth.
- About two seconds after the level starts, the next band's monsters, the next biome's surfaces
  and **this biome's music cues** are warmed in the background, so a transition doesn't pay for
  them at the moment it happens and a new track starts at its first sample instead of fading in
  over a download.
- The self-test empties the texture cache, loads a depth that changes both biome and tier, and
  fails if the level draws anything that wasn't warmed first — then checks that all 35 effects
  were decoded before they could be played.

## Packing: lossy where there is no alpha to protect

```
npm run pack:lossy      # opaque PNGs -> lossy WebP, with a measured PSNR floor
npm run pack:stills     # enemy stills -> WebP fallbacks
```

`tools/lossyWebp.mjs` converts only files whose alpha channel is fully opaque, and decodes each
result back to compare it against the master: anything under 30 dB PSNR is rejected and left as
PNG rather than shipped. 17 files went from 5.43 MB to 0.40 MB at 38.6–45.1 dB. PNG masters move
to `asset_sources/` (git-ignored), the same arrangement as `sprite_sources/` and `music_sources/`.

## What ships: the asset audit

Vite copies whatever the `import.meta.glob` patterns cover, so an asset nothing can name still
downloads for every visitor. `npm run qa:assets` resolves every file in the shipping globs the
way the game does — biome tables, prop kinds, the animation manifest's `sprite|action` keys,
sfx event names, music filename prefixes — and lists what no code path can ask for.

```
npm run qa:assets                 report
node tools/assetAudit.mjs --delete
AUDIT_KEEP="assets/images/ui/menu_bg.png" node tools/assetAudit.mjs --delete
```

`checkBuild` runs it in `--check` mode, so unreachable assets fail the build instead of piling
up. Deletions archive the provenance entry (prompt, seed, model, source URL) to
`assets/images/removed.json` rather than losing it, which keeps regeneration possible if the
call was wrong.

The first version of this tool guessed at the naming rules and reported 47 of 50 animation
clips as dead. Reading the code that resolves keys was the fix, and the rule is now written
down in the tool: an audit that invents deletions is worse than no audit.

## Animation anchors

An animated clip is cropped tight around the moving silhouettes; the still sprite it was
generated from is a padded square. Both are drawn on one billboard quad, so a monster used to
grow by up to 69% the moment it started walking. The bake's framing is recovered into
`assets/anim/manifest.json` (`frame.canvas`, `frame.compose`, `frame.sprite`, the still's
`subject` box and the clip's `medianSubject`), and `src/render/animation.js: bodyRectFor` turns
them into the right quad per clip.

```
node tools/animAnchor.mjs      # after any bake: fills in the framing for every clip
```

Run it whenever `animWebp` produces new clips — the bake writes `frame.canvas/compose`, but the
still's pixel size and silhouette box come from the image manifest. The self-test then measures
the on-screen silhouette of a clip frame against the still of the same creature and fails above
a 10% difference.

## Idle monsters are animation frames, not separate art

A standing creature is drawn from the first frame of its walk cycle, not from the generated
still sprite. Falling back to the still made an orc that stopped moving turn into a different
drawing — a separate illustration at a different silhouette — which is the second half of the
size-jump problem. The stills are still loaded, but only when a browser cannot decode animated
WebP at all, or a clip fails to decode.

```
node tools/stillToWebp.mjs      # enemy stills: PNG masters -> WebP fallbacks
```

That conversion took the 23 species stills from 5.42 MB to 1.18 MB in the build. The PNG
masters move to `sprite_sources/`, which git ignores, because they are the images the
image-to-video clips were generated from. Measured fidelity of the fallbacks: median PSNR
21 dB, mean absolute colour error 11.6/255, and the alpha channel essentially untouched
(worst-case error 1/255), so the cut-out edges survive. They are fallback art now, which is
why that trade is reasonable; if you ever want them pristine, `WEBP_Q=92 node tools/stillToWebp.mjs`
costs about a third more bytes.

## Dev notes

- **The watcher ignores `assets/` and atomic-save temp files.** Watching those two
  things crashes chokidar on Windows with `EBUSY` and takes the whole dev server down —
  the art pipeline writes PNGs while the server runs, and some editors save by writing a
  `.tmp` file next to the source. They are excluded, so source edits still hot-reload.
  Because the image registry is built from a glob at server start, **adding** a new PNG
  means restarting the server. Replacing a PNG under the same name — which is what the
  art pipeline does — only needs a page reload.
- **Stale-code trap:** if a dev server was started before a fix landed and the fix is not
  reaching the browser, restart the server. `npm run test:game` always starts its own
  server, so a passing test can coexist with a stale tab — that is exactly what happened
  once with the strafe fix.
- **Props are real geometry; creatures are still billboards.** `world/propMeshes.js`
  builds crates, barrels, bones, chains, arches, doors, pillars, the staircase, torch
  sconces and loot plinths as low-poly meshes with lit `MeshStandardMaterial`, because
  the headlamp and torch lights have to shape them. Sprites stay deliberately *unlit*
  (`MeshBasicMaterial`) since the generated art has lighting baked in — do not "fix" that
  by lighting the sprites. Prop materials and their texture clones are cached across
  levels and marked `userData.shared`, so level teardown must not dispose them.
- **A prop kind that has no art is skipped, never drawn.** `rubble` and `cobweb` used to
  fall through to `props/rubble` — an asset that was never generated — so the engine drew
  its procedural placeholder: a grey blob sitting in a corridor. `makeProp` now builds both
  as geometry, and the billboard path checks `hasAsset` before drawing anything. The
  integration suite asserts the whole kind list, so a new kind cannot reintroduce it.
- **Wall-mounted means mounted.** Torches hang on the nearest wall face, bracket plate on
  the masonry and arm plus flame out over the corridor; a torch in a cell that is open on
  all four sides is skipped rather than floated in mid-air. The integration suite fails if
  any sconce points at open space instead of a wall.
- **Metalness without reflections goes chalky.** Nothing here has an environment map, so a
  high-metalness material has only the headlamp to reflect and blows out to pale grey right
  in front of it. Iron is authored dark, low metalness, high roughness; the flame is
  authored saturated and `toneMapped: false`, because ACES drags a bright warm emissive
  toward white — which is why the torch read as a cream cone for a while.
- **Ground shadows are drawn, not generated.** The generated `vfx/contact_shadow` sprite
  keys out with a hard edge, and under a pale creature it looked like a hole in the floor.
  `getSoftShadowTexture()` in `render/assets.js` is a radial gradient with no edge to key,
  and it scales with each enemy's tier ramp (smaller and fainter for things that hover).
- **A shot's direction comes from the shooter.** A projectile whose direction defaults to
  the viewer's own facing makes an archer behind you fire away from you, which is precisely
  what an early build did. Enemy shots now carry an explicit direction plus a few degrees of
  spread, and the integration suite asserts that a hostile shot closes the distance to the
  player.
- **Adding to the logic list is not the same as putting it in the scene.** The player's own
  arrows were pushed onto `game.projectiles` without ever being added to the scene graph:
  they existed, spent ammunition and dealt damage, and were never drawn. `spawnProjectile`
  does both — use it for anything that must be seen.
- **Sprite roll lives inside the upright billboard.** `billboardTowards` sets orientation
  before any extra roll is applied; if it only assigned `rotation.y`, each frame would roll
  the sprite a little further and an arrow in flight would end up a spinning blur.
- **Prompts must be affirmative.** The image graph samples at CFG 1 with its negative
  branch wired to `ConditioningZeroOut`, so a negative prompt is thrown away — and a
  `no X` clause typed into the positive prompt is just a description of X, which the
  model then paints. Observed: "no dots" → a lattice of dots, "no blue, no cyan" → blue
  chips. Name the palette and the arrangement instead ("evenly distributed all-over
  detail", "clean unbroken background"). Details in spec §13.2.
- **Solid props never spawn on the entry cell, the staircase cell, or the ring of cells
  around the staircase** (`placeDecor` in `world/levelGen.js`). While props were
  transparent cutouts the overlap was invisible; as geometry it put a door physically on
  top of the way down.
- **Archive folders have to be excluded from the asset glob.** `assets/images/_photoreal_v1/`
  keeps every superseded generation for reference, and the registry globs
  `assets/images/**/*.png` — so the first hosted build shipped all 57 archival PNGs too:
  113 MB instead of 53, every one of them unreachable by the game. The glob now carries a
  negated pattern for `images/_*/**,` and `npm run check:build` prints the file count and
  total size, so a surprise like that shows up before a visitor pays for it.
- **Node is not on PATH** on this machine. Use the full path
  (`C:\Program Files\nodejs\npm.cmd`), and prepend `C:\Program Files\nodejs` to `$env:PATH`
  for scripts that shell out to `node`.
- Levels, spawns, drops and quality rolls all come from one seeded RNG per run, so the
  same seed always produces the same level. Frame-rate-dependent `Math.random()` is
  used only for cosmetics.
